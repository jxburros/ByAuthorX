# Competitiveness implementation plan

Status: **proposed direction, not yet implemented**. Written 16 October 2026 against version 0.3.0.
It complements the [context engine plan](context-engine-plan.md), which covers retrieval, citation, grounding and provenance. This plan covers everything else needed to make ByAuthorX a credible choice for people who write books and long documents.

## 1 Goal

ByAuthorX already has a strong engine, a durable `.byax` master, a typesetting layer and a trustworthy approach to AI. Its gaps against Scrivener, Atticus, Vellum, Ulysses, Word and Grammarly are about **manuscript scale, publishing output, editor interchange, writing-quality depth and reach**, not about the core.

This plan adds those capabilities in five tracks:

| Track | Theme | Main competitors addressed |
| --- | --- | --- |
| A | Manuscript projects: binder, corkboard, goals | Scrivener, Ulysses |
| B | Publishing: EPUB and a compile pipeline | Vellum, Atticus, Scrivener |
| C | Editor and reader interchange, and sync-folder safety | Word, Google Docs, Scrivener |
| D | Offline grammar and fiction analysis | Grammarly, ProWritingAid, LanguageTool |
| E | Reach: macOS, signing, onboarding, extensions | all |

## 2 Invariants this plan must not break

These are the same properties that make ByAuthorX distinctive. Every item is reviewed against them. The invariants in section 2 of the context engine plan also apply.

| Invariant | Consequence for this plan |
| --- | --- |
| **The `.byax` master is authoritative; exports never replace it** | Compile and EPUB are exports with located-loss reports. A project is still one master, never a folder of loose files that is the source of truth |
| **Local-first, no accounts, no telemetry, no background network** | No cloud collaboration, no hosted sync service, no update pings. Sync-folder support is about being safe in folders the user already syncs |
| **AI is opt-in, not opt-out** | Grammar and fiction analysis are deterministic and local. Anything model-based is a separate, opt-in tier |
| **One engine behind GUI, CLI, MCP and REST** | Every new operation is added to `INTERFACE_INVENTORY` and passes `tests/test_interface_parity.py`. No GUI-only features |
| **Proposals before changes** | Fixes suggested by checks or imports of reviewer edits are proposals the writer accepts one by one |
| **Located losses** | Every lossy conversion lists what was lost and where |
| **Deterministic output** | Compiled output is reproducible for the same inputs, with a recorded layout signature (spec 6.4) |
| **Schema changes need a transition function and a fixture** | See `docs/architecture.md`. Projects (track A) are the largest schema change here |

New rule added by this plan: **a feature ships in the CLI and library before, or together with, its GUI.** That keeps automation and testing first-class and matches the interface-parity contract.

## 3 Track A: manuscript projects

### 3.1 Binder and project model (A1)

A book is many scenes grouped into chapters and parts. Today the semantic outline already identifies sections by stable heading ID. The project model builds on that rather than replacing it.

- **Representation.** A `.byax` document gains an optional `project` structure that orders *sections* as binder items. Each item has a stable ID, a kind (`part`, `chapter`, `scene`, `note`, `front`, `back`), a status and optional metadata. The text still lives in the document body, so every existing check, export, history and proposal path keeps working.
- **Operations.** `project move`, `project split`, `project merge`, `project set-status`, `project set-target`. Each is a canonical operation with an exact range, revision precondition and anchor remapping for comments, bookmarks and tracked changes, as split and join already provide (spec 16.5).
- **Non-text items.** Research notes and character sheets are `note` items that are excluded from compile by default (see C-rules in B2). They appear in the binder but not in the manuscript flow.
- **Scope check.** An alternative is a multi-file project. It is rejected for 1.0 because it breaks the single-master invariant, complicates history and breaks interface parity. Revisit only if documents regularly exceed what a single package handles; the benchmark harness decides.

### 3.2 Corkboard and outline views (A2)

- Scene cards with title, synopsis, status, word count and target. Drag to reorder (calls A1 `project move`).
- Synopsis is authored text or empty. It is never silently generated by a model. A "draft a synopsis" action is an opt-in AI proposal.
- Outline view shows the same structure as an indented list with counts.

### 3.3 Goals and sessions (A3)

- Per-document, per-item and per-session word targets; daily goals; streaks.
- Statistics reuse the shared authored, publication and selection counters (issue #5).
- Session records are local preferences, not document revisions, so they never enter history.

### 3.4 Named drafts (A4)

- "Save draft as…" with a note, built on the existing branches and delta history. The words in the UI are *draft* and *compare*, not *branch* and *merge*.
- Compare two drafts at scene level using the semantic comparison already in `compare.py`.

### 3.5 Exit criteria

- A 100,000-word fixture project opens, reorders a chapter and saves inside the measured typing and structural-edit targets in `docs/benchmarks`.
- Splitting, merging and moving scenes preserve every comment, bookmark and tracked-change anchor (property tests).
- Round trip: project to `.byax` to DOCX to import preserves binder order as headings, with a loss report for statuses and targets.

## 4 Track B: publishing

### 4.1 EPUB export (B1)

EPUB is the largest missing format. `docs/file-views.md` already lists it as a candidate after the first release.

- **Output.** EPUB 3 with reflowable text, navigation document built from the outline, embedded fonts where the embedding permission allows (spec 5.2), cover image, metadata and a language tag. Accessibility metadata (`schema:accessMode`, alt text) is included, and images without alt text are reported.
- **Validation.** Output must pass EPUBCheck. EPUBCheck runs in CI as an optional job, because it needs Java. A built-in structural check runs everywhere.
- **Import.** EPUB import is a follow-up, treated like HTML import with the same hostile-archive limits (`_safe_zip`) and a located-loss report.
- **Registry.** Add `epub` to `EXPORT_FORMATS` and the generated view list in `file-views.md`. A read-only EPUB file view is optional.

### 4.2 Compile pipeline (B2)

One command turns a project into a finished book. This is where the layout engine becomes a selling point.

- **Compile profile.** An extension of the export profile (spec 9.2) that chooses which binder items are included, in what order, with what front and back matter, and what each item kind looks like.
- **Book design.** Trim sizes, mirrored margins, scene-break glyphs, chapter openers (drop caps, small caps first line), running heads and folios, and widow and orphan control. Everything reuses the page-master, header/footer and footnote work already verified in the acceptance matrix.
- **Targets.** Print-ready PDF (with bleed and crop marks as an option), EPUB, DOCX for submission, and plain Markdown.
- **Preflight.** Fonts embedded, images at target resolution, missing alt text, orphan headings, empty chapters. Preflight findings use the existing findings model.
- **Determinism.** The compile report carries the `layout_signature` digest. The same inputs yield the same bytes for EPUB and the same page breaks for PDF.
- **Presets.** A small set of well-designed templates (novel, non-fiction, manuscript submission in standard format). Templates are data, not code, and share the existing reusable-settings collections (issue #22).

### 4.3 Exit criteria

- EPUBCheck passes on every fixture.
- Compiled PDF of the 100,000-word fixture is reproducible and its layout signature is recorded in the acceptance matrix.
- A manuscript submitted in standard format round-trips through DOCX with no unreported losses.

## 5 Track C: interchange and sync

### 5.1 Lossless review round trip through DOCX (C1)

Editors still work in Word. This is the first thing a professional editor will test.

- Tighten DOCX import and export for tracked changes, comments with ranges, replies, and moves so that a document sent to an editor and returned maps back to **proposals and comments** in ByAuthorX, never silent edits.
- Compare the returned file against the sent snapshot, so only the editor's changes appear as proposals and the writer's own later edits are not overwritten. The existing branch-merge machinery supplies the three-way logic.
- A "review package" action produces a locked review copy and records its snapshot hash. A "merge reviewed copy" action consumes the returned file.
- Fidelity limits are listed as located losses. Complex field codes and SmartArt are reported, not dropped silently.

### 5.2 Beta-reader round trip (C2)

- Send a read-and-comment copy as DOCX or PDF, and as a self-contained HTML file with offline commenting that exports a comment file. The comment file imports as comments and proposals.
- No hosted service. The writer sends the file however they like.

### 5.3 Sync-folder safety (C3)

Writers keep files in Dropbox, iCloud and OneDrive. The lock and autosave design must survive that.

- Detect cloud-synced folders and warn about risky patterns (open file locks, conflicted copies).
- Detect "conflicted copy" files and offer a merge using the same branch-merge flow.
- Atomic replace and crash-safe save already exist (spec 3.3). Add tests that simulate partial syncs and delayed file appearance.
- This is the safe, local-first substitute for co-editing. The decision in `coediting-spike.md` (no live co-typing; host-serialized batches, section leases and reviewable branch merges) stands.

### 5.4 Exit criteria

- A Word round trip fixture suite (tracked changes, comments, replies, a moved paragraph) produces proposals with the correct ranges, and the located-loss report lists every unsupported construct.
- Conflicted-copy detection merges two divergent edits to different sections with no loss and conflicts on the same section.

## 6 Track D: grammar and fiction analysis

### 6.1 Offline grammar tier (D1)

The deterministic checks (spec 12.1) cover spacing, articles, capitalization and balanced pairs. A rule-based grammar engine would close the biggest quality gap with Grammarly while keeping everything local.

- **Candidate.** A LanguageTool-class rule engine. LanguageTool itself is Java and LGPL, so it would run as an optional, user-installed or downloaded sidecar. A pure-Python rule set is the alternative if the sidecar is too heavy.
- **Decision gate.** Choose by license, size, startup time and accuracy on a fixture corpus. A dependency or download is approved under the same rules as the context engine's model catalogue: shown source, size and checksum, verified before use, never automatic.
- **Integration.** Findings enter the existing findings pipeline with rule, family, severity, exact range and repair proposals. Language is taken from the document or section.
- **Opt-in.** Off until the user installs it. The checks panel shows "not installed" honestly instead of implying coverage (spec 12.3).

### 6.2 Fiction analysis checks (D2)

Deterministic, advisory and tunable per section through the existing section profiles.

- Dialogue tags and attribution variety; adverb density; filter words; repeated sentence openings; word and phrase echoes within a window.
- Sentence-length and paragraph-length rhythm; a pacing graph per chapter.
- Sensory-word balance and "show versus tell" word lists as advisory only.
- Names and terms: inconsistent spellings of invented names, using the codex when the context engine adds it (context engine plan section 8.2).
- All of these ship with off-by-default or low-sensitivity settings so they do not nag.

### 6.3 Readability reports (D3)

- Per-chapter readability and style reports using standard indices, with sample-size caveats in the output.
- Export as a report document with the same located-loss handling.

### 6.4 Languages (D4)

- Dictionary and grammar packs as data: installable, checksummed, versioned.
- Localised interface strings on top of the existing localisation hooks (issue #52). Translation coverage is tracked per language in the docs.

### 6.5 Exit criteria

- Grammar accuracy on a fixture corpus is reported per rule family with precision and recall, and the numbers are published in the docs for each release. This mirrors the context engine plan's "published benchmarks" principle.
- Fiction checks produce no findings on a clean fixture and the expected findings on a seeded one.
- Checks stay incremental: editing one paragraph re-runs only dependent checks (spec 12.4).

## 7 Track E: reach

### 7.1 macOS (E1)

- Port: Qt supports macOS, and the code is largely platform-independent. Audit for Windows and Linux assumptions: paths, credential storage (Keychain), file associations, fonts, printing and the `fontconfig`-style discovery.
- Packaging: a signed and notarized `.dmg` build in `release.yml`. A macOS CI job runs the offscreen suite.
- Scope: Apple silicon first. Intel only if demand justifies it.

### 7.2 Signing and updates (E2)

- Windows code signing, macOS notarization, and Linux package signing.
- Update checking is **opt-in** and manual by default: a "Check for updates" menu item that makes one request when the user clicks. No background polling, consistent with the invariants.

### 7.3 Onboarding (E3)

- A sample project that demonstrates the semantic model (styles, outline, proposals, checks, a citation) and doubles as a regression fixture.
- A short first-run tour with a skip option and a reduced-motion variant.

### 7.4 Extension layer (E4)

- A documented, versioned extension point built on the CLI, MCP and REST surfaces that already exist.
- **Scope for 1.0:** custom checks as data and small scripts (building on the custom checks already supported), export hooks, and saved command macros. Extensions run out of process, with no access to the document except through the same authenticated, scoped operations as any other client.
- No in-process plugin loading in 1.0.

### 7.5 Companion viewer (E5, lowest priority)

- A read-only way to view and comment from a phone or browser, delivered as the self-contained HTML review copy from C2. A native mobile app is out of scope.

### 7.6 Exit criteria

- The offscreen suite passes on macOS, and installers on all three platforms are signed.
- The sample project opens, compiles and passes all checks without findings.

## 8 Sequencing and sizing

Sizes are rough and assume one maintainer working with AI assistance. Each phase is shippable on its own.

| Phase | Items | Depends on | Rough size | Can ship as |
| --- | --- | --- | --- | --- |
| 1 | B1 EPUB export | — | 2–3 weeks | 0.4 |
| 2 | A1 binder model, A2 corkboard and outline, A3 goals | context engine Phase 1 not required | 5–7 weeks | 0.5 |
| 3 | B2 compile pipeline | 1, 2 | 4–6 weeks | 0.5 or 0.6 |
| 4 | C1 Word round trip, C3 sync-folder safety | — (can start with phase 1) | 4–5 weeks | 0.6 |
| 5 | D2 fiction checks, D3 readability, A4 named drafts | 2 | 3–4 weeks | 0.6 |
| 6 | D1 offline grammar, D4 languages | decision gate | 4–6 weeks | 0.7 |
| 7 | E1 macOS, E2 signing, E3 onboarding | 1–3 for sample project | 4–6 weeks | 0.7 |
| 8 | C2 beta-reader round trip, E4 extensions, E5 companion | 4 | 5–7 weeks | 0.8+ |

- **Why this order.** EPUB comes first because it is small, high-value and has no dependencies. The binder follows because the compile pipeline and the context engine's manuscript corpus both need it. The Word round trip comes next because editors will test it before anything else. Grammar is later because it needs a dependency decision.
- **Interaction with the context engine plan.** The binder (A1) supplies the structure that the manuscript corpus (context engine Phase 4) indexes, so those two should share one project index rather than build two. Coordinate before either starts.
- **Parallel work.** Phases 1 and 4 are independent and can run in parallel. D2 and D3 do not need the binder if kept document-scoped first.
- **Pull requests.** Each item splits into reviewable pull requests that pass the existing CI gates (`ruff format --check`, `ruff check`, `mypy`, `pytest` offscreen), update the interface inventory, and add a changelog entry and the documentation that owns the behavior.

## 9 Cross-cutting rules

- **Interface parity.** New operations appear in the CLI reference, MCP, REST and library, and in `INTERFACE_INVENTORY`.
- **Schema.** Binder data is a schema addition with a transition function, a fixture generated by the previous release and a restore test.
- **Performance.** Each feature has a benchmark on the 100,000-word fixture in `docs/benchmarks`. Regressions block merge.
- **Accessibility.** New controls get accessible names and tooltips, and pass the widget-tree walk. Corkboard drag-and-drop has a keyboard equivalent.
- **Motion and brand.** New artwork and animation follow `docs/brand.md`, including reduced motion.
- **Dependencies.** Any new dependency or download goes through the license, size and checksum gate, and is recorded in `docs/third-party-notices.md`.
- **Evidence.** Behavior moves from "implemented" to "verified" only with a named automated test or recorded maintainer verification. The maintainer tests the installed app by hand and does not always commit the evidence. Where the maintainer reports a check as done outside the repository, record that in the acceptance matrix as "maintainer-verified" with the date and platform, rather than leaving the row open.

## 10 What this plan deliberately does not do

- **Real-time cloud collaboration.** It conflicts with local-first and with the co-editing decision.
- **A social or community layer.** No accounts, sharing platform or marketplace.
- **A general note-taking application.** Notes are binder items inside a manuscript, not a second product.
- **Default-on AI features.** Anything model-based stays opt-in.
- **A native mobile app.**
